# Diding - 아키텍처

## 모듈 구성과 계층

```
:apps:diding                   앱 조립 (Application, MainActivity, 셸 명세, DI)
 ├─ feature:splash             버전 확인 관문
 ├─ feature:home               오늘 탭
 ├─ feature:management         관리 탭
 ├─ feature:calendar           캘린더 탭
 ├─ feature:setting            설정 탭
 ├─ core:alarm                 정확 알람 스케줄러 + 발화·재예약 리시버
 ├─ core:database              Room DB, 저장소 구현, 알람 포트, 알림 스위치
 ├─ core:domain                모델·저장소 계약·판정·유스케이스 (순수 Kotlin 성격)
 └─ core:demo-seed             촬영용 데이터 시드 (debug 전용)
```

의존 방향은 `feature -> core:domain` 이고, 구현은 `core:database` 가 갖는다.

- `core:domain` 은 Room·Hilt·Compose 를 모른다. 저장소 인터페이스와 모델만 있고 구현과 Hilt 바인딩은 `core:database` 소관이다. 유스케이스에는 `@Inject` 를 달지 않고 ViewModel 이 저장소를 넘겨 만든다.
- `core:database` 는 Room 을 `implementation` 으로 가두고 `core:domain` 을 `api` 로 재노출한다. database 를 붙인 쪽의 컴파일 경로에는 계약 타입만 오르고 Room 은 오르지 않는다. 저장소 구현체는 `internal` 이다.
- 화면(feature)은 `core:domain` 계약만 본다. 홈·캘린더는 `core:database` 를 아예 의존하지 않고, 관리·설정만 알람 스케줄러 포트를 쓰려고 의존한다(DAO·엔티티는 참조하지 않는다).
- `core:alarm` 은 `MainActivity`·앱 `R` 을 직접 참조하지 않고 공용 `AppLaunchInfo` 포트를 주입받는다. 직접 참조하면 core 가 앱을 거꾸로 의존한다. 바인딩은 앱 모듈에만 둔다.
- 도메인 모듈을 `shared/core` 로 올리지 않은 이유는 요일 규약과 날짜 키 형식이 이 앱의 약속이라 올리면 소비 앱 전체의 계약이 되기 때문이다. 대신 반복 판정 자체는 여러 앱이 쓰는 공용 `recurrence` 모듈에 맡기고, 도메인은 이 앱의 규약을 그 위에 얹는다.

## 셸과 화면 배선

앱은 화면을 나열하지 않는다. feature 모듈이 `FeatureDestination` 을 `@IntoSet` 으로 올리고 NavGraph 는 레지스트리의 집합만 편다.

| 앱이 소유 | feature 가 소유 |
|---|---|
| 탭 라벨·아이콘, 바텀바 표시 규칙 | route 상수와 등록 순서 |
| 셸 명세(바텀바 슬롯·광고 배너)와 `NavHost` 골격 | `composable(ROUTE)` 등록과 화면 본문 |

- `MainActivity` 는 공용 셸 호스트를 상속하고 앱 명세만 넘긴다. 테마·딥링크 배선·`Scaffold`·정책 변경 팝업은 셸이 세운다. 이전에는 이 앱만 셸 배선을 손으로 조립했다.
- 탭 전환 동작(선택 판정, `popUpTo`, 상태 저장·복원)은 공용 `AppBottomNavigationBar` 가 정한다. 바텀바와 배너는 탭 네 개에서만 보이고 스플래시·공지·약관 화면에서는 숨는다.
- 시작 목적지는 스플래시다. 관문을 통과하면 오늘 탭으로 가며 스플래시를 백스택에서 지운다. 딥링크나 알람 알림이 먼저 화면을 열었으면 그 화면을 걷어내지 않는다.
- 화면을 추가하는 순서: 앱에 feature 의존 추가 -> (탭이면) 탭 항목 추가 -> (딥링크면) host 매핑 추가.

## 딥링크

host 와 route 를 잇는 맵 하나가 허용 목록과 라우터 매핑을 함께 낳는다. 둘을 따로 적으면 한쪽만 고쳤을 때 딥링크가 조용히 거부되거나 이동하지 않는다.

- 탭 네 개로 가는 경로 없는 형태만 허용하고 쿼리는 버린다. 모두 공개 등급이며 자사 앱 연동과 App Links 는 쓰지 않는다.
- 자기 패키지는 빌드 값으로 판정해 dev·prod 패키지 차이를 따라간다.
- 콜드 스타트 링크와 실행 중 링크를 같은 큐에 넣고, 셸이 `NavController` 를 라우터에 붙인 뒤 소비한다. 라우터는 탭 바와 같은 규칙으로 이동한다.

## 데이터 모델과 저장

- 할 일과 "날짜별 완료 기록" 두 테이블이다. 같은 날 같은 할 일의 완료는 기본키에서 한 건으로 합쳐지고, 완료 해제는 그 행을 지운다.
- DB 는 공용 암호화 DB 팩토리(SQLCipher + Keystore)로 연다.
- 이미 저장된 할 일은 반드시 `update` 로 고친다. id 가 있는 할 일을 REPLACE 로 다시 넣으면 외래키 CASCADE 로 완료 이력이 지워진다.
- 시각은 엔티티 기본값이 아니라 `TimeProvider` 로 정한다. 기본값이 있으면 호출부가 빠뜨렸을 때 조용히 기기 시각이 박힌다.

## 반복 규칙과 날짜 규약

- 반복은 `sealed interface TodoRepeat`(매일, 매주, 매월, 없음)이다. 새 종류가 생기면 `else` 없는 `when` 이 컴파일 오류로 알려 준다.
- 매월 29~31일 지정은 그 일자가 없는 달의 말일에 해당한다. 판정 자체는 공용 `recurrence` 가 하고, 교체 때 원래 구현과 같은 답을 내는지 패리티 테스트로 확인했다.
- 날짜는 기기 로캘에 흔들리지 않는 고정 형식으로 저장해 기간 조회가 단순 범위 비교로 성립한다.
- 오늘 목록 필터를 SQL 로 내리지 않는다. 반복 판정이 도메인 타입 안에 있어 질의로 옮기면 규칙이 둘로 갈리기 때문이다. 홈 목록과 캘린더 수행률 분모가 같은 판정 함수를 불러 같은 날 같은 답을 낸다.

## 오늘 화면과 시간 처리

- 기준 시각은 `TimeProvider` 가 기기 시간대 자정마다 새로 내고, 그 시각 하나에서 날짜 관련 값을 모두 뽑아 한 화면이 같은 날을 본다.
- 구독 중일 때만 자정 대기가 돈다. 화면이 보이지 않으면 대기도 조회도 멈춘다.
- 완료 토글은 화면 상태를 먼저 바꾸지 않는다. 저장 뒤 완료 Flow 가 다시 내보낼 때 체크 표시가 바뀐다.
- 기기 시계를 직접 읽지 않는 규칙은 시각 의존 로직을 고정 시각으로 테스트하기 위함이다.

## 알람 파이프라인

```
앱 시작 / 설정 토글 / 할 일 저장·보관 / 발화 후 / 부팅·앱 교체
        └─> 스케줄러 전체 재예약  ──> 할 일마다 다음 발화 시각에 one-shot 정확 알람
발화 리시버 -> 상태 재검증 -> 알림 발송 -> 전체 재예약
```

- 반복 알람 API 대신 매번 one-shot 을 다시 건다. 주간·월간 규칙이 고정 간격이 아니기 때문이다. 여러 번 예약해도 할 일당 알람은 하나만 남게 한다.
- 알림 마스터 스위치 판정은 스케줄러 안에 둔다. 예약을 요청하는 경로가 여럿이라 판정을 호출부에 두면 하나만 빠뜨려도 꺼 둔 알림이 되살아난다. 꺼져 있으면 그냥 돌아가지 않고 이미 예약된 알람을 거둔다.
- 발화 시점에도 보관·알림 여부를 다시 본다. 예약 뒤 상태가 바뀌었을 수 있다. 알림 발송이 실패해도 재예약은 따로 돈다.
- 리시버 선언과 권한은 앱이 아니라 그것을 쓰는 모듈 매니페스트에 둔다. 발화·정확 알람 권한 변경 리시버는 `core:alarm`, 재부팅·앱 교체 재예약 리시버는 공용 `fundamental:alarm` 에 있다. 의존에 넣는 행위 자체가 배선이 되게 하려는 것이다.
- 재부팅·앱 교체 리시버에 `android:permission` 을 걸지 않는다. 받는 시스템 액션이 모두 protected broadcast 인데 검사를 걸면 앱 교체 브로드캐스트가 조용히 배달되지 않는다.
- 전면 취소 대상 id 는 저장소에서 받는다. id 범위를 훑으면 호출 스레드가 멈추고 상한 밖 id 가 남는다.

## 앱 시작

`Application` 은 공용 시작 클래스를 상속해 공용 시작 작업(Activity 추적, 권한 SDK, Crashlytics, 광고 동의)을 먼저 돌린 뒤 알림 채널을 만들고 전체 재예약을 IO 스코프에서 부른다. 스코프 문맥의 예외 처리기를 빼면 재예약 예외가 콜드 스타트를 죽이므로 반드시 둔다. 빠져나온 예외는 Crashlytics 로 보고된다.

## 관리 화면의 상태 모델

관리 화면은 MVI(State, Intent)를 쓴다. 공개 액션이 많아 `onIntent` 단일 진입점이 낫고, 하위 컴포저블은 콜백만 받아 ViewModel 을 모른다. 목록은 Room Flow 가 출처라 로딩·오류 상태를 타입에 만들지 않는다. 저장은 시트를 먼저 닫은 뒤 재예약을 부른다. 재예약 실패가 저장 실패 처리로 번져 시트가 남고 재저장 시 중복되는 것을 막기 위해서다.

## 설정 화면과 권한

알림 켜기는 권한이 허용됐을 때만 설정 값과 토글을 올리고, 영구 거부면 토글을 끄고 앱 설정으로 안내한다. 권한 요청은 공개 SDK `net.plumt.permission` 이 맡는다. 권한 확보, 설정 저장, 알람 예약/취소는 유스케이스 하나로 묶는다. 설정 키 문자열의 사본을 만들지 않는다(설정 화면과 스케줄러가 같은 값을 읽어야 어긋나지 않는다).

## 빌드

- 규약 플러그인 일곱 줄이 빌드 구성의 뼈대다. 선언 순서는 `ModuleConventionGuard` 가 검사한다
- 플레이버·서명은 규약 플러그인이 만들고 앱에서 다시 선언하지 않는다
- `preBuildVerify` 는 설정 JSON 구조, 매니페스트 딥링크 스킴, release 서명, 운영 광고 키를 검사한다. 운영 광고 키가 비면 운영 릴리스가 멈추는 것은 의도다
- 릴리스는 R8 축소를 켠다. 앱 규칙은 최소이고 SDK 규칙은 각 모듈 몫이다

## 알려진 함정

- 스키마 v1 은 파괴적 마이그레이션 허용 상태라, 그대로 스키마 버전을 올리면 데이터가 전부 삭제된다
- 알람 리시버 클래스 위치나 액션 문자열을 바꾸면 이미 예약된 알람이 발화도 취소도 되지 않는다
- 시작 재예약 실패는 처리기가 흡수해 조용하다. 알람이 빠진 채 앱이 정상으로 보일 수 있어 Crashlytics 보고로 확인한다
