# Lottomate 아키텍처

앱 모듈(`:apps:lottomate`)은 조립만 하고, 데이터·도메인은 `core`, 화면은 `feature` 모듈이 갖는다. 규약 플러그인의 `AppModuleShapeGuard` 가 앱 모듈에 허용 밖 파일·디렉터리·컴포넌트 선언이 생기면 구성 단계에서 빌드를 멈춘다. 이 규칙은 앱 직속에 쌓였던 코드 약 1만 줄을 feature 모듈로 분해한 뒤 지키고 있다.

## 모듈 계층

```
:apps:lottomate  (Application · MainActivity · DI · 내비게이션 배선)
 ├─ feature/*    화면 + 상태홀더 (splash, home, my-numbers-overview, my-numbers, statistics, more, notifications, messaging)
 ├─ core/*       데이터·도메인 (common, database, winning-numbers, winning-checker, countdown, my-numbers, statistics, receipt-import, demo-seed)
 └─ shared/*     여러 앱이 공유하는 기반 (app-shell, designsystem, firebase, 순수 로직 모듈 ...)
```

- feature 는 core 를 의존하고, core 는 feature 를 의존하지 않는다. 한때 화면 모듈끼리 서로 참조해 data·domain 을 core 로 옮겼고, 화면 부품 재사용 몇 건만 계층 가드 예외로 남았다.
- `core/common` 은 회차 모델, 등수 판정, 번호 계산, 번호 UI, 테마, 토픽 구독을 모은 앱 공용 모듈이다.
- 다른 앱에도 있던 순수 로직(반복 시각 계산, 수명 있는 캐시, 트랜잭션 포트, 기간 집계)은 공용 모듈로 올리고 앱 쪽 중복 구현을 지웠다. 교체할 때는 원래 구현과 같은 답을 내는지 패리티 테스트로 확인했다.

## 시작 순서

1. `Application` 이 모듈들이 기여한 시작 작업(오류 보고 설치, Crashlytics, 광고 SDK)을 돌린다.
2. 서로 기다리지 않는 IO 코루틴 둘이 Remote Config 초기화와 알림 토픽 갱신을 한다.
3. `MainActivity` 가 공용 셸 호스트에 앱 명세를 넘기면 셸이 테마·딥링크 배선·바텀바·정책 변경 팝업을 세운다.
4. 내비게이션은 스플래시에서 출발한다. 스플래시가 버전 관문을 통과하면 당첨번호를 동기화하고 홈으로 간다.

초기화 코루틴 스코프는 `SupervisorJob` 기반이고 예외 처리기를 문맥에 가진다. 빠져나온 예외는 Crashlytics 로 보고되고 프로세스는 살아 있다. 과거에 이 처리기가 없어 초기화 예외가 콜드 스타트를 끝내는 문제가 있었다.

## 내비게이션

- 탭 4개(홈·내 번호·통계·더보기)와 보조 목적지(알림함·공지사항·약관 웹뷰)로 나뉜다. 스플래시는 홈으로 갈 때 백스택에서 빠진다.
- 바텀바는 공용 `AppBottomNavigationBar` 에 탭 목록만 넘기는 래퍼다. 표시 여부는 각 목적지가 직접 켜고 끈다.
- 배너 광고가 바텀바 슬롯 안에 있어 바텀바가 숨는 화면에서는 광고도 함께 숨는다. 종료 확인 팝업은 뒤로 가기가 앱을 떠날 때만 뜬다.

## 딥링크

host 와 route 를 잇는 맵 하나에서 허용 목록과 라우터 매핑이 함께 파생된다. 두 곳에 따로 적으면 한쪽만 고쳤을 때 링크가 조용히 거부되거나 이동하지 않기 때문이다.

외부 앱이 열면 안 되는 목적지(알림함)는 자기 발신만 허용한다. 알림함 항목을 누르면 앱이 자기 패키지를 발신자로 디스패치해 그 경로를 통과한다. 이전에는 모든 항목이 공개 등급으로 만들어져 외부 앱이 알림함을 열 수 있었고 이를 고쳤다. 스플래시 관문을 지나기 전에 들어온 링크는 보류했다가 관문 통과 뒤 전달한다.

## 데이터 흐름

```
Firestore(최신·회차·전 회차) ──> core/winning-numbers ──> core/database (SQLCipher Room)
                                                          ▲
feature/my-numbers* ──> core/my-numbers ──────────────────┤
feature/statistics ───> core/statistics ──────────────────┘
FCM 데이터 메시지 ──> feature/messaging ──> core/winning-checker ──> 로컬 알림
```

- **당첨번호**: 앱은 Firestore 만 읽는다. 외부 로또 사이트 수집은 별도 저장소의 서버가 맡는다. 최신 회차는 공용 TTL 캐시를 거친다. 서버 응답에서 비어 있는 금액·당첨자 수는 같은 회차의 기존 행 값으로 채워, 부분 응답이 기존 데이터를 지우지 않게 한다.
- **로컬 DB**: SQLCipher 로 암호화한 Room DB 다. 키는 Android Keystore 로 보호한 passphrase 를 공용 모듈에서 만든다. 파괴적 마이그레이션을 켜지 않고 명시적 `Migration` 으로만 올린다. 사용자가 저장한 번호를 스키마 변경으로 조용히 지우지 않기 위해서다.
- **당첨 확인**: 단말이 주기적으로 깨어나 확인하지 않는다. 발표 시각을 아는 쪽이 서버라서 서버가 FCM 데이터 메시지를 보내면 `feature/messaging` 의 핸들러가 `core/winning-checker` 를 부른다. 푸시에 담긴 당첨번호로 대조해 DB 동기화를 기다리지 않는다.
- **카운트다운**: `core/countdown` 은 시각을 인자로만 받는 순수 판정이고, 반복 시각 계산은 공용 `recurrence` 모듈에 맡긴다. 갱신 상태홀더는 `feature/home` 에 둔다. 서버 시각 보정은 `time-sync` 공유 모듈이 맡는다.
- **번호 불러오기**: `core/receipt-import` 가 QR 우선, 아니면 글자 인식으로 넘어가는 판별과 파싱·회차 검증을 갖고 화면은 `feature/my-numbers` 에 있다. QR·ML Kit 타입은 data 계층 밖으로 내보내지 않고 domain 은 포트만 안다. 인식 결과는 사용자가 확인한 줄만 저장한다.
- **시각 처리**: 엔티티와 도메인 모델의 생성·수정 시각에 기본값을 두지 않고 호출부가 `TimeProvider` 로 채운다.

## UI 패턴

- 상태는 `state` 로 읽고 사용자 액션은 `onIntent(Intent)` 로만 보내는 MVI 스타일이다. 토스트·URL 열기 같은 1회성 이벤트는 별도 채널로 보낸다.
- 화면은 공용 Paper 컴포넌트(티켓 스텁 디자인)로 분해돼 있다. 각 탭 화면 파일이 1천 줄을 넘던 것을 수백 줄 단위로 줄였다.
- 스플래시·설정 화면 뼈대는 공용 `SplashScaffold`, `SettingsScaffold` 에 위임해 앱마다 문구와 모양이 갈라지지 않게 한다.
- 통계 ViewModel 은 UseCase 호출마다 예외를 따로 받아 한 섹션의 실패가 다른 섹션을 비우지 않는다.

## 설정과 시크릿

- 설정 값은 저장소 밖 앱별 설정 파일에서 읽고, 환경(dev·prod)에 따라 일부 값을 바꾼다.
- 빌드 시 설정 생성 단계가 암호화한 C 소스를 만들고 NDK 로 빌드해 JNI 로 복호화한다. 소스 리터럴과 달리 dex 에 평문이 남지 않는다. 키마다 접근자가 생성되므로 키를 지우면 그것을 부르는 코드가 컴파일되지 않는다.
- 광고 단위 id 는 공용 모듈이 운영 값으로 담고 개발 빌드의 시험 광고 전환은 광고 모듈이 한다. 운영 광고 키가 비었거나 테스트 id 면 운영 릴리스 빌드가 검증에서 멈춘다.
- 환경 판정의 근원은 플레이버다. 빌드 타입이나 applicationId 로 추론하지 않는다.

## 알려진 유의사항

- 앱 백업이 꺼져 있어 재설치 시 내 번호가 복원되지 않는다.
- 릴리스에서 `android.util.Log` 호출을 모두 제거하므로 릴리스 원인은 Crashlytics 로 본다.
- 시스템 스플래시 테마는 API 31 부터 적용되어 minSdk 29~30 기기는 같은 색의 창 배경을 본다.
